# SweepstakesWiz Odds Calculator — Design Specification

**Status:** Approved  
**Date:** 2026-07-30  
**Canonical route:** `/tools/sweepstakes-odds-calculator/`

## 1. Problem and context

SweepstakesWiz needs an organic-search and trust asset that answers a concrete player question—“What are my chances of winning?”—and then gives the reader a relevant path to the site’s editorial casino rankings. The calculator must improve on the reference at `playwithstakes.com/tools/sweepstakes-odds-calculator/` without copying its unsupported modes or presenting estimates as known odds.

The current project is a mixed Astro application. Authored app routes live under `src/routes/`, are copied into the generated and gitignored `src/pages/` tree by `scripts/generate-astro-pages.mjs`, and use `src/layouts/ContentLayout.astro`. That layout already provides canonical metadata, visual breadcrumbs, the compliance ribbon, GA4, shared nav/footer chrome, and one consolidated JSON-LD graph through `src/lib/schema.ts`. Existing visual conventions live in `partials/trust.css`; `src/components/CurrencyCompare.astro` and `CurrencyFlow.astro` are the closest patterns for self-contained, responsive, accessible explanatory components.

There is no `/tools/` hub today. The guide `src/content/guides/dual-currency-sweepstakes-model.mdx` already tells readers to “Use our live tools,” making it a natural first spoke.

## 2. Goals and non-goals

### Goals

- Rank for sweepstakes odds, sweepstakes calculator, multiple-prize odds, and adjacent free-entry/AMOE questions with substantial server-rendered editorial content.
- Produce mathematically defensible probabilities for exact drawings without replacement.
- Keep the default experience understandable with three fields and one plain-language result.
- Clearly separate known-pool calculations from estimated-pool scenarios.
- Explain the effect of free and paid entries without repeating the reference page’s counterfactual error.
- Lead interested readers to three currently top-ranked casinos while preserving editorial, affiliate, age, location, and responsible-play disclosures.
- Preserve privacy: all entered values and calculations remain in the browser.

### Non-goals

- Tournament, leaderboard, rank, or “weighted” odds.
- Simulation or Monte Carlo results when an exact expression is available.
- Predicting an operator’s undisclosed pool, player behavior, or future entries.
- Scraping operator data, accepting uploads, saving calculations, accounts, or sharing result URLs.
- Comparing expected monetary value, purchase efficiency, payout size, or recommending spend.
- Claiming that casino rankings are generated by the calculator.

## 3. Reference-page rationale

V1 deliberately does not reproduce the reference page’s problematic behavior:

- Its “weighted” mode does not apply actual weights and labels a without-replacement hypergeometric calculation as Bernoulli.
- Its no-purchase counterfactual removes paid entries from the user’s numerator but leaves those same entries in the pool denominator.
- It accepts `K > N` and reports 100% instead of rejecting an impossible drawing.
- Its factorial implementation is incompatible with its billion-entry claim because intermediate factorials overflow long before that scale.
- Its copy gives both “1 in 250” and the correct “1 in 500” for the same `M=1, N=5000, K=10` example.
- Its tournament mode is an uncalibrated rank-only heuristic. SweepstakesWiz will not present that as probability; tournament support remains out of scope until a defensible model and validation data exist.

## 4. User journey

1. The reader lands on the tool from search, `/tools/`, navigation, or a relevant guide.
2. Above the fold, a short sentence explains that the calculation assumes unique winning entries drawn without replacement.
3. The default form shows only:
   - **Your entries**
   - **Total entries**
   - **Number of prizes** (default `1`)
4. A small **I don’t know the total** control replaces **Total entries** with **Your best estimate of total entries**. It does not add more visible fields.
5. The reader selects **Calculate my odds**. The form is handled entirely client-side; it never submits or changes the URL.
6. A valid known-pool result starts with one sentence such as **“Your calculated chance is 1 in 500.”** An unknown-pool result starts with **“Your estimated chance is about 1 in 400 to 1 in 625 (base estimate: 1 in 500).”**
7. Secondary result text shows the percentage, assumptions, and an explicit “estimate” label where applicable.
8. Immediately below the result, three editorially top-ranked casino cards appear under **“Get more free entries at these sweepstakes casinos.”**
9. **More options** contains collapsed **Compare free vs paid entries** and **Multiple drawings** controls.
10. **How this works** contains formulas, assumptions, the three entry-mix definitions, the estimate-band method, caveats, and worked examples.
11. Server-rendered sections answer the main search intents and end with a visible FAQ and related links.

## 5. Architecture and components

### Route and rendering

- Author the page at `src/routes/tools/sweepstakes-odds-calculator/index.astro`.
- Let `copyAppRoutes()` in `scripts/generate-astro-pages.mjs` copy it into `src/pages`; never hand-edit the generated page.
- Use `ContentLayout.astro`, shared `partials/trust.css`, and scoped component styles.
- Set `export const prerender = false` because the casino CTAs must use the existing geo-aware `<AffiliateLink>` path. Editorial copy, initial form markup, methodology, FAQ, disclosures, and cards still render on the server.
- Keep only calculation behavior client-side. With JavaScript disabled, the explanatory article, methodology, FAQ, links, and casino reviews remain usable, and a `<noscript>` message explains that the calculator itself needs JavaScript.

### Proposed separation

- `src/routes/tools/sweepstakes-odds-calculator/index.astro` — page composition, SEO copy, schema nodes, FAQ, and top-three ranking lookup.
- `src/routes/tools/index.astro` — lightweight, prerendered tools hub linking to this tool and future tools.
- `src/components/odds/OddsCalculator.astro` — semantic form, result regions, expandable options, and a bundled vanilla TypeScript controller. No UI framework dependency.
- `src/components/odds/OddsCasinoRecommendations.astro` — three geo-aware editorial cards using `AffiliateLink`.
- `src/lib/sweepstakesOdds.ts` — pure parsing-independent probability, estimate-range, entry-mix, repetition, and display helpers; no DOM, analytics, or Astro dependencies.
- `scripts/verify-sweepstakes-odds.ts` — deterministic assertions using `node:assert/strict`, matching the repository’s verification-script convention.

The tool route reads the current order from the existing `comparisons/sweepstakes-casinos` content entry and takes its first three `partnerSlugs`; names, availability, brand identity, and outbound behavior continue to come from existing editorial/affiliate data. Do not create a second ranking list inside the tool.

### Site integration

- Add `/tools/` to shared nav and footer, and link the calculator from `/tools/`.
- Add contextual links from the dual-currency, AMOE, Sweeps Coins, no-deposit, and relevant official-rules content where the link improves the reader’s next step.
- Register `/tools/` and `/tools/sweepstakes-odds-calculator/` in `writeSitemapAndRobots()`, including explicit authored source paths in `sourcePathsForUrl()` so `lastmod` comes from git history instead of the fallback date.

## 6. Data model and formulas

All accepted values are base-10 safe integers. Let:

- `M` = the user’s entries.
- `N` = total entries in the drawing, including the user’s entries.
- `K` = unique prizes/winning entries drawn without replacement.
- `D` = repeated independent drawings with the same stated pool conditions.
- `F` = free/AMOE entries owned by the user.
- `P = M - F` = the user’s paid or purchase-associated entries.

### Exact single-drawing probability

The chance of at least one win is:

`p = 1 − C(N−M, K) / C(N, K)`

with `0 ≤ M ≤ N` and `1 ≤ K ≤ N`. Special cases are explicit: `M=0` gives `p=0`; `M>0` and `K>N−M` gives `p=1`.

Do not compute factorials or raw combinations. Compute the no-win probability in log space and return `p = -expm1(logNoWin)`. Use the shorter of these equivalent products to bound loop count:

- Over prizes: `logNoWin = Σ(i=0..K−1) log1p(−M/(N−i))`
- Over user entries: `logNoWin = Σ(i=0..M−1) log1p(−K/(N−i))`

Clamp only final floating-point noise to `[0,1]`; never use clamping to make an invalid scenario appear valid. This is an exact combinatorial model evaluated numerically, not a simulation.

### Unknown-pool estimate

The single entered estimate `E` means estimated **total entries including the user’s entries**. Derive a deterministic uncertainty band:

- low-pool assumption: `Nlow = max(M, K, floor(0.8E))`
- base assumption: `Nbase = E`
- high-pool assumption: `Nhigh = ceil(1.25E)`

The `0.8×` and `1.25×` factors are reciprocal on a multiplicative scale. They are a product heuristic, not a confidence interval or operator data. Display the resulting chance from the low pool first (best chance), then the high pool (worst chance), with the base result alongside it. Every result, label, and schema-visible description in this mode must use “estimated,” “about,” or “assumption”; never call it “real odds.”

All three derived pools must be safe integers. Reject an estimate whose high bound would exceed `Number.MAX_SAFE_INTEGER`.

### Entry-mix comparison

When **Compare free vs paid entries** opens, ask only **How many of your entries were free/AMOE?** and derive `P=M−F`. Calculate three distinct quantities:

1. **Combined current-pool odds:** `exact(M, N, K)`.
2. **Free-only odds in the same current pool:** `exact(F, N, K)`. Paid entries remain in the denominator because they still exist in the actual drawing, but they are not counted as the user’s target entries.
3. **No-purchase counterfactual:** `exact(F, N−P, K)`. The user’s own paid entries are removed from both numerator and denominator.

The primary comparison may summarize combined versus no-purchase odds. The same-current-pool free-only distinction belongs in **How this works** and in an accessible expanded result, so the simple view does not imply those quantities answer the same question.

For estimated pools, run all three calculations at `Nlow`, `Nbase`, and `Nhigh`, removing `P` from each counterfactual denominator. If any selected counterfactual produces `K > N−P`, block the selected comparison with a specific correction rather than converting it to 100%.

### Repeated drawings

For `D` independent drawings with the same single-drawing probability `p`:

`pD = 1 − (1−p)^D`

Evaluate as `-expm1(D * log1p(-p))`, with explicit handling for `p=0` and `p=1`. Copy must state that this assumes independent drawings and a stable pool/probability. If entries roll over, the pool changes, or draws are linked, the result does not apply.

### Display rules

- Lead with reciprocal odds (`1 in X`) and show the percentage immediately below.
- Use adaptive significant digits; do not display false precision. Reciprocal odds use at most three significant digits and “about” when rounded.
- Preserve the exact known example: `M=1, N=5000, K=10` displays `0.2%` and `1 in 500`.
- For `p=0`, say **“No chance with zero entries.”** For `p=1`, say **“Certain under these inputs (100%).”**
- Never use “guaranteed win” outside the mathematical `p=1` boundary and its stated assumptions.

## 7. UI states and copy hierarchy

### Initial state

- Three visible fields, one primary button, the unknown-total link, and a one-line assumptions summary.
- Inputs are blank except **Number of prizes = 1**. Do not show an empty result, zero, or a fabricated example as the user’s answer.
- **More options** and **How this works** use native `<details>/<summary>` elements and are closed by default.

### Valid result

1. Plain-language reciprocal answer.
2. Percentage and whether the pool is known or estimated.
3. Short assumption line: unique winning entries, without replacement.
4. Optional free/paid and repeated-drawing summaries.
5. Casino cards and disclosures.
6. Methodology expansion and worked examples.

Recalculation replaces the existing result in place and moves focus to the result heading only after an explicit button activation. It must not append duplicate result regions.

### Editorial section order

1. What this calculator tells you.
2. What to do when total entries are unknown.
3. How multiple prizes change the result.
4. Free/AMOE entries versus purchase-associated entries.
5. Multiple independent drawings.
6. Assumptions and limitations.
7. Worked examples, including the `1/500` case and an estimated range.
8. Methodology and formulas.
9. Visible FAQ.
10. Related tools and guides.

## 8. Validation and error behavior

Validation runs on button activation and blocks all calculation and analytics completion events until every active scenario is valid. Show an error summary above the form, focus it, and link each message to its field; also show the message inline with `aria-describedby`.

- Missing value: **“Enter your total entries.”**
- Negative value: **“Your entries can’t be negative.”**
- Decimal or exponent: **“Use a whole number of entries.”**
- Unsafe integer: **“Enter a whole number smaller than the calculator’s maximum.”**
- `M > N`: **“Total entries must include your entries, so it can’t be smaller than your entries.”**
- `K > N`: **“The number of prizes can’t be greater than the total entries.”**
- `K < 1`: **“Enter at least one prize.”**
- Estimated `E < M`: **“Your estimated total must include your entries.”**
- Estimated `E < K`: **“Your estimated total can’t be smaller than the number of prizes.”**
- Derived estimate overflow: **“Use a smaller estimated total so the full range can be calculated.”**
- `F < 0` or `F > M`: **“Free entries must be between 0 and your total entries.”**
- Counterfactual `K > N−P`: **“Without your paid entries, this scenario would have more prizes than entries. Adjust the entry split or prize count.”**
- `D < 1` or non-integer: **“Enter at least one whole drawing.”**

Switching pool mode clears the inactive pool field and its errors. Closing an advanced option removes that option from the active calculation but does not silently change the three base inputs.

## 9. Conversion behavior and compliance

Directly below a valid result, render three cards under **“Get more free entries at these sweepstakes casinos.”** The cards:

- Follow the current first-three order from the existing best-casinos editorial content.
- Link to each review and use `AffiliateLink` for the CTA, including geo suppression and a placement such as `odds-calculator`.
- May mention free-entry routes already supported by existing editorial data, but must not invent or freeze new bonus values in the calculator.
- State: **“These are editorially ranked casinos, not recommendations produced by your odds result.”**
- Include the existing affiliate disclosure treatment, **18+ (21+ where required)**, state availability, no-purchase, and responsible-play language.

No calculated probability, input, or entry type changes card order, card visibility beyond existing geo rules, CTA wording, or ranking. Do not emit `Offer`, `Product`, `Review`, `AggregateRating`, or rating claims for this block.

Render the card markup on the server immediately after the result container. It remains visible with a review-first framing when JavaScript is unavailable; a successful calculation simply places the populated result directly above it.

## 10. SEO, schema, and internal linking

### Search presentation

- Use a descriptive title and meta description centered on exact sweepstakes odds, multiple prizes, and free-entry comparison.
- Keep the calculator and its direct answer above the long-form copy.
- All key explanations and FAQ answers are server-rendered; do not hide the primary editorial answer in client-only markup.
- The `/tools/` hub should be concise, indexable, and linked from shared nav/footer.

### JSON-LD

Use the existing consolidated graph and stable IDs:

- `WebPage` from `ContentLayout`: `<canonical>#webpage`.
- `BreadcrumbList` from `ContentLayout`: `<canonical>#breadcrumb`.
- `WebApplication`: `<canonical>#app`, with truthful `name`, `url`, `description`, `applicationCategory: "UtilitiesApplication"`, `operatingSystem: "Any"`, `browserRequirements: "Requires JavaScript"`, `isAccessibleForFree: true`, and publisher `{"@id":"https://sweepstakeswiz.com/#organization"}`.
- `FAQPage`: `<canonical>#faq`, matching visible questions and answers exactly.

Set `mainEntityId` to `<canonical>#app`. Every internal `@id` reference must resolve in the same graph under `buildPageGraph()`. Do not emit offers, ratings, expected winnings, unsupported accuracy claims, or values derived from a visitor’s inputs.

### Required internal links

Include natural, restrained links to:

- `/tools/`
- `/guides/dual-currency-sweepstakes-model/`
- `/guides/amoe-sweepstakes-casinos/`
- `/guides/sweeps-coins-explained/`
- `/bonuses/no-deposit/`
- operator reviews for official-rules context
- `/state-legality/` and `/sweepstakes-tracker/`
- `/how-we-rate/`
- `/legal/affiliate-disclosure/`
- `/responsible-gaming/`
- `/best/sweepstakes-casinos/` once, in a restrained editorial context

The page must tell readers to check the applicable operator’s official rules; SweepstakesWiz calculations do not override published rules or disclose an unknown pool.

## 11. Analytics and privacy

Calculations are local and ephemeral. Do not submit a form, call an API, put inputs in query parameters, write them to storage, or include them in logs.

Allow only these coarse GA4 events:

- `odds_calculation_completed` — boolean/enum metadata only, such as known versus estimated mode and whether an advanced option was active.
- `odds_options_opened` — option name from the fixed enum `entry_mix` or `multiple_drawings`, once per option per page view.
- `odds_casino_cta_clicked` — casino slug and fixed placement.

Never send `M`, `N`, `K`, `D`, `F`, `P`, estimate bands, calculated probability, reciprocal odds, validation values, or any bucket derived from those numbers. Analytics failure must never block calculation or navigation.

Fire `odds_calculation_completed` once per successful explicit **Calculate my odds** activation, never on keystrokes or failed validation. Treat input text as untrusted: parse it without evaluating code and never insert it into HTML.

## 12. Accessibility

- Use a real `<form>`, visible `<label>` elements, fieldsets/legends for mode choices, and native buttons.
- Keep logical keyboard order and visible focus indicators; all controls must work without a pointer.
- Use `inputmode="numeric"` with whole-number validation and programmatic names/instructions.
- Errors use text and icons in addition to color, with an error summary and field-level associations.
- The result heading receives programmatic focus after calculation; the result body uses `aria-live="polite"` without announcing every keystroke.
- Native details/summary controls expose expanded state without custom keyboard scripting.
- Maintain WCAG AA contrast, 44px minimum touch targets where practical, responsive single-column behavior, and reduced-motion support.
- Casino availability and estimated status must never rely on color alone.
- No-JS users retain the full article, FAQ, disclosures, and links.

## 13. Test plan and acceptance criteria

### Automated probability checks

`scripts/verify-sweepstakes-odds.ts` must cover:

- Known example: `M=1, N=5000, K=10` → `p=0.002`, `0.2%`, `1 in 500`.
- Single prize identity: `K=1` → `p=M/N`.
- Large pool: at least `M=1, N=1_000_000_000, K=1`, finite and accurate without overflow or `NaN`.
- Boundaries: `M=0`, `M=N`, `K=N`, and `K>N−M`.
- Every invalid relationship and unsafe/non-integer input.
- Estimate example `E=5000, M=1, K=10` → pool assumptions `4000/5000/6250` and odds `1 in 400 / 1 in 500 / 1 in 625`.
- Estimate monotonicity: larger pool never produces a better chance with fixed `M,K`.
- Entry mix `F=2, P=3, N=100, K=1`: combined `5/100`, free-only current pool `2/100`, no-purchase counterfactual `2/97`.
- Estimated entry-mix counterfactuals remove `P` from all three denominators.
- Repeated drawings match `1−(1−p)^D`, including `p=0`, `p=1`, `D=1`, and a large `D`.
- Result formatting at tiny probabilities, rounded reciprocals, zero, and certainty.

### Integration and content checks

- Keyboard-only completion, mode switching, both details controls, recalculation, and CTA navigation.
- Error summary focus, inline associations, result announcement, contrast, zoom/reflow, and screen-reader labels.
- No-JS response contains the article, methodology, FAQ, disclosures, cards/review links, and `<noscript>` calculator notice.
- Network/GA inspection confirms entered and derived numbers never leave the page.
- Casino cards match the first three current `partnerSlugs`, preserve geo suppression, and do not claim mathematical recommendation.
- JSON-LD contains one consolidated graph with resolvable `#webpage`, `#breadcrumb`, `#app`, and `#faq` IDs; visible FAQ parity passes; no offer/rating schema appears.
- Generated sitemap contains both tool URLs and uses authored-source git dates for `lastmod`.
- `npm run content:lint`, `npm run methodology:check`, `npm run schema:verify`, `npm run verify:availability`, the new odds verifier, `npm run build`, and the repository CI command pass.

### Acceptance criteria

V1 is accepted when a new user can obtain the `1 in 500` answer from three fields, an unknown-pool user gets a clearly labeled range, every invalid active scenario is blocked with a corrective message, advanced calculations match the definitions above, editorial content works without JavaScript, no entered number is transmitted, and rankings/schema/sitemap behavior passes the repository gates.

## 14. Rollout

1. Implement and verify pure helpers and formatting first.
2. Build the calculator and route; verify keyboard, no-JS, and privacy behavior locally.
3. Connect the cards to the existing ranking and geo-aware affiliate path.
4. Add schema, `/tools/`, internal links, nav/footer entries, and sitemap source mapping.
5. Run all repository gates and inspect generated HTML/JSON-LD.
6. Validate on a preview deployment at mobile and desktop widths, including one eligible and one suppressed location.
7. Publish indexable routes together so the calculator is never orphaned. Monitor coarse completion, option-open, CTA, crawl, and indexing signals; do not infer calculation quality from CTA conversion.

No migration or user-data backfill is required. If analytics or cards fail, the calculator and editorial content must continue to work.

## 15. Explicit future expansion

Possible later work includes additional exact draw structures, saved/shareable scenarios with an explicit privacy design, operator-supplied pool integrations with provenance, localization, and a calibrated tournament model. None belongs in V1. Tournament odds may be added only when the inputs, probability model, calibration evidence, limitations, and validation suite are strong enough to avoid a rank-only heuristic.
